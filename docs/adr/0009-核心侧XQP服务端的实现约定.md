# 0009 核心侧 XQP 服务端的实现约定
- 状态：提议
- 日期：2026-10-04；决策人：待 A 评审

## 背景
按 17 第 1 节实现 `wind_input/crates/wind-xinqing-tap`（任务 A-03）时，有几处与 17 的写法不同，或者规格没有写到。

## 决策
1. **消息类型与帧编解码用心晴工作区的 `xqp` crate**（Hub、xq-sim 已在用），不再按 17 第 1.1 节另写 `event.rs`，也不依赖 `wind-ipc`。三方共用一份类型，契约仍是 `protocol/xqp.schema.json`。
2. **队列用标准库 `sync_channel(4096)`**，不引入 crossbeam-channel。钩子只调 `try_send`，满了计入 `dropped`，行为与 17 相同。
3. **`ts` 在钩子里打，不在写线程补**。写线程排队会让按键间隔失真，而 IKI 是状态识别的核心特征。`ts` 是相对 `Tap::start` 的毫秒数，同一 `session` 内单调。
4. **焦点状态与“最近上屏”缓冲用 `Mutex`，不用 ArcSwap**。两者只在协调器线程（焦点、上屏、进入改写）和收到 `cfg` / `pause` 时访问，不存在争用；按键与组字钩子不碰锁，只读原子量。
5. **同一焦点只发一次 `focus`**：`(app, scope, blocked)` 与上次相同就不发；闸门从关到开（收到 `cfg{collect:true}`、无痕关闭）时补发一次当前焦点，Hub 不必等下一次切换应用。
6. **Hub 断开即撤销同意**：`collect`、`send_text`、`rewrite` 全部置假，等新连接的 `cfg`。另外写线程只把采集事件写给已收到 `cfg{collect:true}` 的连接，新连接在 `cfg` 之前收不到旧连接留下的事件。
7. **核心自己切换的无痕状态不随重连同步**。Hub 重连后只在它认为无痕开启时补发 `pause{on:true}`（ADR 0007 后续），核心若在断线期间自行开启无痕，会保持开启直到用户再次切换。这个方向只会少采集，不会多采集。
8. **不认识的下行消息类型跳过，不断开**。10 第 2.1 节说 JSON 无法解析时关闭连接，这里照做；但 JSON 合法、只是类型或字段不认识时跳过，因为协议只会新增消息类型和可选字段。
9. **命名管道用重叠 I/O**。同步句柄上一个线程阻塞读时，另一个线程的写会排在后面，写线程会被读线程卡住。

## 备选方案与取舍
第 3 条也可以按 17 在写线程补 `ts`，实现更简单，但队列积压时（例如 Hub 卡顿）所有按键会挤到同一毫秒，没有采用。

## 影响
17 第 1.1、1.2、1.4 节（文件结构、`Tap` 字段、写线程补 `ts`）；10 第 2.1 节（非法帧的界定）。接受后同步修改产品书并在 00 第 5 节记录。
