# 0010 状态解释的信号挑选与拼句
- 状态：接受
- 日期：2026-10-04；决策人：B（提议）、D（同意，见 D 交接文档第 4 节）、E（同意，2026-10-04）

## 背景
实现 FR-STA-09（`xinqing_hub/core/src/domain/explain.rs`）时，规格只说“取 |z| 最大的 2–3 个特征，加上本地规则提示”，
没有说两者怎么排、与显示状态对不上的信号要不要说，也没有说只有本地规则（没有可能性）时句子怎么拼。

## 决策
1. **只说与显示状态相符的信号**。各状态认的信号：犹豫——停顿、放弃、删已上屏、翻页、间隔长、慢、删改多；
   低落——慢、间隔长；烦躁——快、删改多、节奏乱、手误；疲劳——时长、深夜、慢、删改多、手误、间隔长。
   否则会出现“看起来有点低落 · 打字速度比平时快 20%”这种自相矛盾的解释。一条相符的都没有时，才退而说现有的信号。
2. **流畅不罗列偏离**。回到 `fluent` 时只说 `note.no_signal`（“节奏和平时差不多”），即使某个 z 分数超过阈值。
3. **规则证据排在 z 分数前面**（停顿、放弃、删已上屏、手误、翻页、时长、深夜），z 分数信号按 |z| 从大到小，
   最多 3 条。这与规格示例的顺序一致（“停顿了 3 次 · 打了又删 · 慢 35%”）。
4. **同一信号只说触发窗口的值**，上一个窗口只用来补充触发窗口没有的信号。
5. **结构化输出**：后端返回 `Explanation { state, prob_pct, signals[{kind, value}], source, cold_start }`，
   界面按 `explain.toml` 的文案键拼句，**版式由界面自己定**（例如小组件悬停时分多行）；`note.format` 那种单行格式和
   后端的 `ExplainCopy::render` 只给回放工具、评测和文案校验用。`prob_pct` 是 0–100 的整数百分比，
   和 `StatusSnapshot.prob`（0–1 小数）用名字区分（D 评审意见）。
6. **没有可能性时**（只有本地规则、冷启动）去掉“（可能性 …%）”一段；冷启动附注追加在来源之后。
7. `explain.toml` 中 `format`、`separator`、`max_signals` 写在 `[note]` 表之后，按 TOML 语法属于 `[note]`
   （前端生成的键也是 `explain.note.format`）。保持现状，不改模板键，避免前端文案键变化。
8. `{p}` 的分母 `med` 用当前生效的基线中位数：冷启动时是人群默认值，之后是个人值。

## 备选方案与取舍
- 严格按字面“|z| 最大的 2–3 个特征 + 全部规则提示”：规则提示多时会超过 3 条，且会说出与状态矛盾的信号，没有采用。
- 由后端直接返回整句：前端无法换语言或调整排版，也和“前端只用文案键”的做法不一致（10 第 5.1 节 UiError），没有采用。
