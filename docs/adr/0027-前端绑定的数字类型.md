# 0027 前端绑定的数字类型
- 状态：提议
- 日期：2026-10-05；决策人：D（提议，`bindings.ts` 契约负责人）；待 C（`domain/settings.rs` 的 `SettingValue` 属设置键注册表契约、对话命令的外壳类型）、
  B（`SelfReportItem`）评审

## 背景
`bindings.ts` 里所有 `f64` 字段都导出成 `number | null`，包括时间戳这类永远有值的字段（`ChatSessionItem.created_ts`、`SelfReportChanged.until_ts`、
`ResearchInvite.answer_until_ts`……），前端只能到处写 `?? 0`，也分不出哪些字段真的可能为空。`SettingValue` 也因此多了一个 `null`。

原因在 specta-typescript 0.0.12（`primitives.rs`）：`f32` / `f64` 一律导出成 `number | null`，因为 `serde_json` 把 NaN、Infinity 序列化成 `null`。
它提供两种绕开的办法：

- `Configuration::enable_lossless_floats()`：全局把浮点改成 `number`，前提是“运行时保留 NaN / Infinity”。Tauri 的 IPC 走 `serde_json`，不满足，
  而且对真的可能算出 NaN 的浮点（比如以后的比例、平均值）也会去掉 `null`，类型就不诚实了。
- 字段上标 `#[specta(type = specta_typescript::Number)]`：只把这一个字段导出成 `number`，由写的人担保它不会是 NaN。

（ADR 0018、0026 的 D 评审已指出这个问题，说好单独提契约 PR。）

## 决策
1. **不会是 NaN 的 `f64` 字段标 `#[specta(type = specta_typescript::Number)]`**，导出成 `number`。这一版标了：
   - 时间戳（Unix 毫秒，由整数换算而来）：`ChatSessionItem.created_ts` / `last_ts`、`ChatMessageItem.ts`、`MemoryItem.created_ts`、`ChatSearchItem.ts`、
     `NetLogView.ts`、`SelfReportItem.ts`、`SelfReportChanged.until_ts`、`ResearchInvite.answer_until_ts`；
   - `SettingValue::Number`：值从 JSON 读进来（库里的 JSON 文本、前端传入的参数），JSON 没有 NaN，写入时还按 `Kind` 校验范围。
     前端类型由 `boolean | number | null | string | string[]` 变为 `boolean | number | string | string[]`。
2. **真的可能为空的保持 `number | null`**，它们在 Rust 里本来就是 `Option`：`StatusSnapshot.prob`、`Routine.avg_stop_min`、`RoutineNight.stop_ts` / `stop_min`、
   `Signal.value`、`NetLogView.latency_ms` 等。前端看到 `| null` 就该处理空值。
3. **以后新加 `f64` 字段**：能保证不是 NaN 的（时间戳、由整数换算的值）标 `Number`；算出来的比例、均值可能是 NaN 的，保持默认的 `number | null`，
   或者在 Rust 里先处理掉 NaN 再标。`core` 在 `specta` 特性下加了可选依赖 `specta-typescript`（与外壳同一版本）才能在领域类型上标注，
   用 `#[cfg_attr(feature = "specta", specta(type = specta_typescript::Number))]`。
4. **守住时间戳**：`xinqing_hub/src/api/bindings.test.ts` 检查生成的 `bindings.ts` 里名为 `ts` 或 `*_ts` 的字段都是 `number`，可空的列在清单里
   （目前只有 `stop_ts`）；新加时间戳忘了标注，前端测试会失败。
5. 只改导出的 TypeScript 类型，**序列化结果不变**：Rust 端字段类型、JSON 内容、数据库都不动；前端去掉了对话窗口里两处已不需要的 `?? 0`。

## 备选方案与取舍
- 全局 `enable_lossless_floats()`：前提不成立（`serde_json` 不保留 NaN），也会把可能为 NaN 的浮点一起变成 `number`，没有采用。
- 时间戳改用 `i64` 再标 `Number`：`i64` 的语义更准，但要改各处的字段类型和计算代码，牵动 B、C 的领域类型；`f64` 存毫秒在 2^53 以内是精确的，
  只改导出类型就够了，没有采用。
- 做一个 `UnixMs` 新类型统一处理：同样要改所有字段的类型和构造处，收益只是少写一行标注，没有采用。

## 影响
10 第 5.1 节“命令规范”补一句：不会是 NaN 的浮点字段导出成 `number`，可空字段才带 `| null`。
`SettingValue` 的前端类型去掉 `null`（10 第 6.2 节设置值的四种形态本来就没有空值）。接受后同步修改产品书，并在 00 第 5 节记录。
