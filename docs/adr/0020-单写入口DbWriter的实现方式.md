# 0020 单写入口 DbWriter 的实现方式
- 状态：提议
- 日期：2026-10-05；决策人：C（提议，Hub 骨架与数据库的契约负责人）；待 B（感知任务写库）、D（外壳命令）、E（可靠性与测试）评审

## 背景
17 第 2.9 节规定：所有写操作经 `DbWriter`（单线程，`mpsc` 通道），普通数据每 5 秒或满 100 条批量提交；用户确认类数据
（日程、日记、记忆、同意）用 `write_sync` 同步提交，成功后才返回界面（NFR-REL-03）。此前外壳只有一个 `Mutex<Db>`，
读写都排同一把锁：感知任务写窗口、网关写出网日志、界面读设置互相等待（C 交接文档“已知问题”）。

## 决策
1. **一个写连接 + 一个读连接**。写连接交给 `DbWriter`（`core/src/infra/store/writer.rs`），所有写入都经过它；读连接
   `Db::open_reader` 只读，`AppState::db()` 返回它。WAL 模式下读不等写。两个连接都设 5 秒 `busy_timeout`。
2. **写连接用互斥锁串行，而不是专门的写线程 + `mpsc` 通道**。现有的领域函数（`settings::set`、`consent::set`、
   `feedback::record`、对话服务等）都接收 `&Db`，并且在一次调用里读写交错；走通道就得把每次写入改成 `'static` 闭包、
   参数全部克隆、返回值再经通道传回，几十处调用都要改写。互斥锁保证的性质相同：同一时刻只有一个写入者，批量与同步的语义见下。
   另有一个定时线程 `xq-db-writer` 负责按时提交排队的数据。
3. **普通数据排队批量提交**：`DbWriter::enqueue(label, job)`。满 100 条立即提交，否则最早一条排满 5 秒时由定时线程提交；
   一批在一个事务里执行，每个任务一个保存点，某条失败只回滚这一条并记日志（只有标签，不含用户数据）。走这条路的是：
   特征窗口和状态记录（同一个任务，一起成功或一起丢弃）、出网日志、休息提醒记录与作息洞察的每日汇总计数（`routine::record_rest` / `record_active_minute`，B-09）。代价是这些数据最多晚 5 秒才能读到。
4. **用户确认类数据同步写**：`DbWriter::write_sync(|db| …)` 先提交排队中的数据，再在调用方线程上执行，返回时已经落盘。
   **先提交排队的数据**保证先后顺序：例如点“不准”时 `feedback::record` 要“记到最近一条状态记录”，最近一条状态记录可能
   还在队列里。走这条路的是：同意、设置、状态反馈、自评、暖心话记录与反馈、重置 / 重算基线、对话（对话服务读写交错，
   用 `DbWriter::lock()` 拿写连接）、删除对话、数据保留清理。`write_sync` 不包事务（领域函数自己可能开事务）。
5. **读连接在 debug 构建下设 `query_only`**：漏走 `DbWriter` 的写入在开发和测试时直接报错；release 构建不设，避免漏网的写入
   在用户那里直接失败。
6. **退出时提交队列**：`DbWriter` 析构时提交剩下的数据；Tauri 退出时不一定析构托管状态，所以 `RunEvent::Exit` 里再显式
   `flush()` 一次。进程被强制结束时最多丢最近 5 秒的普通数据，用户确认类数据不受影响。

## 备选方案与取舍
- 照 17 的字面做写线程 + 通道：见第 2 条，改动面大，收益相同，没有采用。
- 批量提交时一直开着事务、5 秒后提交：其他写入（同步写）要等这个事务，最长 5 秒，界面会卡，没有采用；现在是排队到提交时才开事务，
  一批 100 条以内的插入是毫秒级。
- 读连接也用 `query_only` 发布：见第 5 条，没有采用。

## 影响
17 第 2.9 节（`DbWriter` 的实现方式、走批量的数据清单、`write_sync` 先提交队列）。B：感知任务的 `save_window`、休息提醒的 `log` / `active_minute` / 提醒弹出时的汇总计数已改为排队，
`recompute_baseline` 走同步写；以后新加写库的地方一律经 `AppState::writer()`。不加迁移，表结构不变。
